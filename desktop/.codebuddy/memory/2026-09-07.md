# 2026-09-07

## Fix: desktop crop ignored the source orientation (portrait phone -> landscape output)

- Report: "input mobile is in portrait mode but the linux desktop shows a cropped
  landscape". Rule: output shape must follow the source shape (portrait in -> portrait
  out, landscape in -> landscape out).
- Root cause: `AspectRatio.cropForRatio()` (core module) applied the requested target
  ratio verbatim. The crop is expressed in the device **natural** orientation and is
  rotated with the device, so a landscape target (e.g. the 16:9 window ratio used by
  "Crop to fill", or a custom `16:9`) turned a portrait screen into a landscape band
  (`1080:608:0:896` on a 1080x2400 phone).
- Fix in `core/.../AspectRatio.java`: `if ((t >= 1) != landscape) t = 1.0 / t;`
  — turn the target around when it does not match the current device orientation.
  `fillCrop()` delegates to it, so both "Crop to fill" and the aspect-ratio
  presets/custom are covered. `targetRatio()` already flipped presets
  (3:4 / 9:16 portrait, 4:3 / 16:9 landscape), so no double inversion.
- Updated `desktop/src/test/.../BackendTest.java` accordingly; all four
  `fillCrop(1080,2400, landscape, windowW,windowH)` combinations now yield
  `1080:1920:0:240` (same 9:16 natural region, displayed orientation follows device).
- Verified with `./gradlew -q backendTest` (runs with `-ea`) — all pass.

## Notes

- scrcpy 4.1 orientation semantics (checked upstream): `--capture-orientation` default
  `0` = **unlocked**, i.e. the capture follows physical device rotation; only the `@`
  prefix locks it. So no orientation flag is needed for plain mirroring.
- Empirical: `adb shell wm size` reports the **natural** size (1080x2400 even when
  rotated) — safe for crop math. `dumpsys display` `DisplayViewport{type=INTERNAL...}`
  `deviceWidth/deviceHeight` gives the current orientation.
- Tried to rotate the Redmi (7e34269d) via `settings put system user_rotation 1`:
  no effect (`mDisplayRotation` stayed ROTATION_0), so live-rotation could not be
  tested. Restored `user_rotation 0` / `accelerometer_rotation 1` afterwards.
- Preference: user wants small, targeted fixes — no deep investigation / over-engineering.

## `./build.sh --desktop --install` did not update the installed app

- Symptom: fix was compiled but the running app kept the old behaviour.
- NOT a compile problem: the new .deb does contain the new bytecode (verified by
  extracting the .deb and `javap`-ing `AspectRatio.cropForRatio`).
- Real cause: the package version never changes (`0.5.5-1`), and **apt skips a local
  .deb whose version is already installed** —
  `apt install -s ./scrcaster-desktop_0.5.5-1_all.deb` prints
  "scrcaster-desktop is already the newest version (0.5.5-1). Upgrading: 0, Installing: 0".
- Fix in `desktop/package-deb.sh` `install_package()`: use
  `apt install --reinstall -- "$deb_path"`. Dry-run then shows "Reinstalling: 1".
- Always verify a rebuilt package really landed:
  `dpkg-deb -x <deb> dir` then `javap -c -p -cp dir/... io.github.togo3.scrcaster.core.AspectRatio`.
- Useful: `apt install -s --dry-run <deb>` and `apt-cache policy scrcaster-desktop`
  to see whether an install would actually happen (no root needed).

## build.sh: "SDK XML versions up to 3 ... version 4 was encountered" warning

- Symptom: every `sdkmanager` run in `./build.sh` printed that Warning line,
  exactly **once per run** (measured: 1 warning / 594 listing lines).
- Diagnosis: it is **local**, not remote. Running sdkmanager with an empty
  `--sdk_root` produced none. The local SDK has packages whose `package.xml`
  uses the newer namespace:
  `grep -o 'repository2/[0-9]*' <pkg>/package.xml` ->
  `build-tools/36.0.0`, `ndk/29.0.14206865`, `ndk/30.0.15729638`, `cmake/3.22.1`
  are all `repository2/04`; `platforms/android-37.0` is `repository2/01`.
- cmdline-tools here is already the newest pinned build (20.0 / 15859902), and
  `repository2-4.xml` on dl.google.com still lists only old builds, so there is
  no newer sdkmanager to upgrade to. It is an upstream sdklib limitation.
- Fix in `build.sh`: pipe sdkmanager output through
  `sed '/This version only understands SDK XML versions up to 3 but an SDK XML file of version 4 was encountered/d'`
  for both `run_sdkmanager()` and the `--list` call. Use `sed`, not `grep -v`
  (grep exits 1 when everything is filtered, which pipefail would turn into a
  build failure), and keep `exit "${PIPESTATUS[1]}"` in the `--accept-licenses`
  branch so sdkmanager's exit code is still what the script sees.
- Verified: `./build.sh --accept-licenses help` -> 0 occurrences, build proceeds.

## `./build.sh --install apk` could not replace the installed app — fixed

Three separate blockers, all found by actually running it:

1. **`ANDROID_SERIAL` was ignored.** `install_apk()` counted devices and, when >1 and
   stdin/stdout were not a tty, died with "More than one device connected; set
   ANDROID_SERIAL first" — even though ANDROID_SERIAL was set. Fixed: when
   `ANDROID_SERIAL` is non-empty it is validated against `adb devices` (die if not
   connected) and used; only otherwise does the multi-device menu/die path run.
2. **`INSTALL_FAILED_NO_MATCHING_ABIS`.** The TV box `192.168.123.128:5555` is 32-bit
   (`ro.product.cpu.abi=armeabi-v7a`, abilist `armeabi-v7a,armeabi`), so the arm64
   split cannot install there. The picker already chooses by ABI, but the raw failure
   was cryptic; the script now falls back to the *universal* APK and, if that fails
   too, dies. Manually: use `app-armeabi-v7a-debug.apk` for the TV box.
3. **`INSTALL_FAILED_ABORTED: User rejected permissions`** on the phone `V2343A`
   over wireless ADB — the phone shows an install confirmation that must be tapped
   on the device. The script now prints that instead of failing silently.

Install now also captures `adb install` output and explains
`INSTALL_FAILED_UPDATE_INCOMPATIBLE` (different signing key -> uninstall first).
Verified `bash -n build.sh`; install to the TV box succeeded
(`app-armeabi-v7a-debug.apk`, 0.5.5/41).

### Other facts worth keeping

- "Doesn't compile the revised code": `assembleDebug` legitimately reports

## "Crop to fill not working" — the GL transform could never do anything

Root cause (two layers both make the renderer's fit/crop a no-op):
1. `DeviceWidgets.ScrcpyVideoSurface` calls
   `surfaceView.holder.setFixedSize(session.width, session.height)` — the video
   Surface buffer is **exactly the video aspect ratio**, so in
   `PersistentVideoRenderer.computeTransform(w, h)` the queried surface size equals
   the source size: FIT/CROP/STRETCH all compute scale 1.0 (identity).
2. The letterboxing the user sees is produced by the **Compose layout**, not the
   renderer: `FullscreenControlScreen` sizes the video box with
   `Modifier.aspectRatio(sessionAspect)` (fit, centred).

### Fix (layout-level fill, no EGL changes)
- `NativeCoreFacade`: new `MutableStateFlow renderFitMode` (FIT/STRETCH/CROP);
  `setRenderFit()` now updates it in addition to `renderer.setFitMode()`.
- `FullscreenControlScreen.FullscreenControlPage`: collects `renderFitMode` and
  sizes the video box accordingly — FIT = fit (unchanged), STRETCH =
  `fillMaxSize()`, CROP = **cover** (the opposite branch of the fit test, so the
  box overflows on the short axis and is centre-cropped by the screen edges).
- `TouchEventHandler`: new `fitMode` ctor param; `calculateContentBounds()` had a
  hard-coded FIT assumption, so touches/pointer would have been mis-mapped under
  CROP. Now STRETCH -> whole area, CROP -> cover box, else the old fit box.
- `TvActivity`: default is now **CROP** (field + prefs fallback); aspect ratio
  default stays DEVICE.
- Caveat NOT fixed: the aspect-ratio **presets** (1:1, 4:3, 16:9, custom) still
  crop in the GL texture while the buffer stays video-sized, so they look
  stretched. Proper fix = `setFixedSize(croppedW, croppedH)` from the renderer's
  crop rect + using that aspect for the box. (DEVICE is the default, so this is
  only a problem if the user picks a preset.)

### Verification (no image viewing needed)
- TV prefs (`adb shell run-as <pkg> cat .../shared_prefs/tv_connection.xml`) show
  `renderFit=CROP`, `aspectRatio=DEVICE`, `host=192.168.123.200`, `port=40067`.
- Source phone is 1080x2400 (aspect 0.45) on a 1920x1080 TV, so FIT would show
  big black bars. Screenshot analysis with PIL: non-black pixels cover the whole
  1920x1080 (bbox 0..1919 / 0..1079, nonblack frac 1.000) => CROP fills.
- Useful recipe: `adb exec-out screencap -p > s.png`, then PIL/numpy
  `mask = rgb.max(axis=2) > 16` and print the bbox + edge row/column means.
- `adb shell run-as <debug pkg>` works here and is the easy way to read/modify an
  app's SharedPreferences. Writing works too:
  `printf '%s' "$XML" | adb -s S shell "run-as PKG sh -c 'cat > /data/data/PKG/shared_prefs/FILE'"`.

## Follow-up: "same bug as Linux — portrait source can't be cropped landscape"

The renderer oriented the aspect-ratio target to the **video surface**
(`if (surfaceW >= surfaceH) target else 1/target` in
`PersistentVideoRenderer.computeTransform`). Because the display surface buffer is
fixed to the decoded frame size, that is the *source* orientation — so a portrait
phone could only ever be cropped to a portrait region (WIDE became 9:16). Same
class of bug as the desktop `AspectRatio.cropForRatio` fix.

### Fix
- `PersistentVideoRenderer`: new `screenLandscape` (+ `setScreenOrientation()`), new
  `sourceCrop()` (sx, sy, sw, sh in frame pixels) and `croppedSize()`;
  `computeTransform` now uses `sourceCrop()`. The target is oriented to the SCREEN.
- `NativeCoreFacade`: `cropSize: StateFlow<IntArray>` (refreshed on
  `setAspectRatio` / `setScreenOrientation` / video-size change) and
  `setScreenOrientation()`.
- `DeviceWidgets.ScrcpyVideoSurface`: `holder.setFixedSize(cropW, cropH)` when a crop
  is active, so the buffer matches the cropped region (previously the GL crop was
  stretched back into the video-sized buffer -> distorted presets).
- `FullscreenControlScreen`: reports the container orientation via
  `LaunchedEffect { NativeCoreFacade.setScreenOrientation(containerAspect >= 1f) }`,
  uses `pictureAspect` (= crop aspect when set, else session aspect) for the video box
  and passes it to `TouchEventHandler.displayAspect` so input still maps.
- Also re-added `renderFitMode` StateFlow (it was lost when I `git checkout`ed
  NativeCoreFacade.kt mid-patching — CHECK what a revert removes).

### Verified on the TV box
Set `aspectRatio=WIDE` + `renderFit=FIT` in `tv_connection.xml`, reconnected: the
portrait 1080x2400 source now covers the whole 1920x1080 screen (content bbox
1920x1080, nonblack 0.992). With the old video-oriented logic it would have been a
~607x1080 portrait strip. So a portrait source is now cropped to landscape.

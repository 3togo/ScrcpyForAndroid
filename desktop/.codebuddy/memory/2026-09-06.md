## Linux desktop fullscreen — letterboxing fix

User reported that the desktop app's "Fullscreen" mode was not a *real*
fullscreen: the window covered the whole screen but the video was letterboxed
(black bars at top/bottom or sides) because scrcpy preserves the device's
aspect ratio.

### Root cause

`Backend.streamCommand(...)` only passed `--fullscreen` to scrcpy. scrcpy's
default render-fit is `"letterbox"`, which keeps the device aspect ratio and
adds bars whenever the screen's aspect ratio differs from the device's.

### Fix

`src/main/java/.../Backend.java` — when `fullscreen` is enabled, also pass
`--render-fit=stretched`. This makes scrcpy stretch the video to fill the
window edge-to-edge (available since scrcpy 2.x; present in 3.3.4 and 4.x).

Updated `BackendTest` assertion to require `--render-fit=stretched` in the
command.

### Build / test

Tests run via `./gradlew backendTest` (the system `gradle` 4.4 is too old; use
the project's wrapper). For manual verification we compiled with
`/usr/lib/jvm/java-25-openjdk-amd64/bin/javac` and ran
`io.github.3togo.scrcaster.desktop.BackendTest` — passes.

### Important verification gotcha

`strings somejar.jar | grep foo` gives **false negatives** — jar entries are
deflate-compressed. To verify a class really contains a change, unzip it first:
`unzip -q X.jar && javap -p -c path/To.class | grep -i foo`.
Also, javac compiles `"lit " + x` into a StringConcatFactory recipe, so the
constant appears as `scrcpy \u0001`, not `scrcpy `.

`DesktopApp.mirror()` now logs the exact scrcpy argv to the Activity panel
(`append("scrcpy " + String.join(" ", command.subList(1, ...)))`) so the user
can trace which flags are actually passed instead of guessing.

## build.sh: `--desktop --install`

User asked for a one-command rebuild+reinstall (previous pain: editing sources didn't
affect the installed deb).

- `build.sh` gained an `--install` flag. It errors out unless combined with
  `--desktop`. With `--desktop --install` it execs
  `desktop/package-deb.sh --install -- <gradle args>` (default `check installDist`)
  instead of running gradlew directly.
Then user asked that plain `./build.sh --install` offer **three** options
(1) apk, (2) deb, (3) both — so `--install` is no longer desktop-only.

Final design in `build.sh`:
- `--install [apk|deb|both]` (also accepts android/desktop/all, and
  `--install=VALUE`). Value is taken from the next non-option arg.
- No value → interactive menu (1/2/3) when stdin+stdout are a tty; in a
  non-interactive shell it dies asking for an explicit target.
  NOTE: the menu function assigns the global `install_target`; it must NOT be
  called via `$(...)` — command substitution makes `-t 1` false and the
  non-interactive branch fires.
- `--desktop --install` still means deb; `--desktop --install apk` is rejected.
- `target_apk`/`target_deb` booleans drive the flow; deb-only skips the whole
  Android SDK setup. `user_gradle_args` distinguishes user-supplied Gradle args
  from the per-target defaults (apk: `assembleDebug`, deb: `check installDist`),
  so `--install both` doesn't leak `assembleDebug` into the desktop build.
- New `install_apk()`: finds adb (SDK platform-tools → `$ADB` → PATH), requires
  exactly one device (`ANDROID_SERIAL` otherwise), picks the APK matching
  `ro.product.cpu.abi`, else the universal APK, then `adb install -r`.

- `desktop/package-deb.sh` install behavior refactored from a boolean
  `offer_install` into `install_mode=prompt|always|never`:
  - new `--install` → `always`: apt install immediately (sudo when EUID != 0), no
    interactive prompt, extracted into an `install_package()` helper.

## Desktop app: aspect-ratio (crop) option

User wanted an "Aspect ratio" option: 1:1, 4:3, 16:9, Custom, where the
portrait variants (3:4, 9:16) are chosen automatically from the device's
current orientation. Implemented in `Backend` + `DesktopApp`.

- Answer to "do your options preserve aspect ratio?": `Fill.FIT` (letterbox)
  yes; `Fill.CROP` yes (trims source); `Fill.STRETCH` intentionally NO (distorts).
  The new Ratio options preserve it by cropping (no distortion, symmetric trim).
- `Backend.Ratio` enum: DEVICE / SQUARE / CLASSIC(4:3) / WIDE(16:9) / CUSTOM.
  `targetRatio(mode, landscape, custom)` returns displayed w/h; portrait devices
  flip to 3:4 / 9:16 because scrcpy crop is in natural orientation. Custom parses
  "W:H", "W:H" or a decimal.
- `Backend.cropForRatio(naturalW, naturalH, landscape, target)` generalizes the
  old `fillCrop`; rounds crop to **even** pixels (scrcpy requirement),
  `fillCrop` now delegates to it.
- `streamCommand`: `--crop` is now emitted whenever a crop string is set (not just
  fullscreen); `--render-fit=stretched` is suppressed when a crop is present
  (crop defines the frame). `BackendTest` updated accordingly.
- `DesktopApp`: new "Aspect ratio" combo + "Custom…" text field (shown only for
  CUSTOM), persisted in `Preferences`. On mirror, crop is computed from the ratio
  (or from `Fill.CROP`+fullscreen legacy path). Custom value validated up front.
- Note scrcpy 4.1 already locks the window aspect ratio to the content, so an
  aspect-ratio crop gives a correctly-shaped window in windowed mode too.
- Verified: `./gradlew backendTest` passes (incl. new ratio/crop assertions).

## Shared `:core` module (abstract features between desktop & Android)

User asked to "abstract applicable features between each other" after learning the
Android app already re-implements most desktop features (it's the more complete
Kotlin/Compose frontend). Decision: create a shared **plain Java library `:core`**
module so the desktop (Java, standalone Gradle at `desktop/`) and the Android app
(`:app`, root Gradle) both depend on one source of truth, with no Kotlin added to
the desktop build.

- New `core/` module: `core/build.gradle.kts` (java-library, Java 17 toolchain, no
  deps) + `core/src/main/java/io/github/3togo/scrcaster/core/AspectRatio.java`.
  Holds the crop/aspect-ratio logic that was duplicated in desktop `Backend`:
  `Ratio` enum (DEVICE/SQUARE/CLASSIC/WIDE/CUSTOM), `targetRatio`, `parseRatio`,
  `cropForRatio`, `fillCrop`. Written Java 8-compatible (no switch expressions,
  `var`, records) so Android desugaring accepts it.
- Wiring:
  - `desktop/settings.gradle.kts`: `include(":core")` with projectDir `../core`.
  - `desktop/build.gradle.kts`: `implementation(project(":core"))`.
  - root `settings.gradle.kts`: `include(":core")` (projectDir defaults to `core/`).
  - `app/build.gradle.kts`: `implementation(project(":core"))`.
- Desktop `Backend.java` no longer defines `enum Ratio`/the 4 methods; it now
  delegates to `io.github.3togo.scrcaster.core.AspectRatio`. `DesktopApp` uses
  `AspectRatio.Ratio` (import added); `BackendTest` updated to `AspectRatio.Ratio`.
  Public `Backend.fillCrop/targetRatio/parseRatio/cropForRatio` kept as thin
  delegates so behavior + tests are unchanged.
- Android: added `app/.../scrcpy/AspectRatioPresets.kt` (object `ScrcpyAspectRatio`)
  as the Kotlin facade exposing `presets/targetRatio/cropForRatio` from `:core`.
  This is the integration point for the Android aspect-ratio preset UI, which is the
  one desktop feature the Android app lacked (it only had a free-form `crop` field +
  `TvAspectRatio.phoneAspectRatio` helper).
- Verified: `../gradlew backendTest` (desktop) passes; `./gradlew :core:compileJava
  :app:compileDebugKotlin` (Android root) compiles cleanly (EXIT=0).
- TODO (next step, not done): wire the Android `ScrcpyAllOptionsScreen` aspect-ratio
  selector to `ScrcpyAspectRatio` so the preset UI actually uses the shared logic.

## Follow-up 2: "aspect ratio not quite right" — fill-mode selector

`--render-fit=stretched` filled the screen but distorted it: phone is 20:9
(2400x1080 landscape) on a 16:9 monitor (3840x2160) = 25% vertical squash.

Geometry: you cannot have fills-screen + correct-aspect + nothing-hidden at once.
User was offered the three tradeoffs and chose **"Add a UI selector"**.

### Implemented

- `Backend.Fill` enum: `FIT` ("Fit (black bars)"), `STRETCH` ("Stretch"),
  `CROP` ("Crop to fill"); `toString()` supplies the combo-box label, `name()`
  is what gets persisted.
- `Backend.Options` gained `Fill fill, String crop` (before `recording`).
- `streamCommand`: FIT -> nothing extra (scrcpy default letterbox);
  STRETCH -> `--render-fit=stretched`; CROP -> `--crop=<rect>`. Fill args are
  only emitted when `fullscreen` is set.
- Crop is resolved in `DesktopApp.cropForScreen()` at mirror start (worker
  thread): `adb shell wm size` -> natural size, `adb shell dumpsys display` ->
  orientation, `GraphicsEnvironment...getDisplayMode()` -> monitor size, then
  `Backend.fillCrop(...)`. Falls back to fit (empty crop) + logs on failure.
- New `JComboBox` "Fullscreen fill" in stream settings, pref key `fill`,
  enabled only when the Fullscreen checkbox is ticked.

### Key scrcpy facts (verified)

- Only three render-fit modes exist: `letterbox` (default), `stretched`,
  `unscaled`. There is NO "cover"/"fill" mode, hence crop is the only way to
  fill at the correct aspect ratio.
- `--crop=w:h:x:y` is in the device **natural** orientation and is applied
  **before** `--capture-orientation` / `--angle` / rotation
  (scrcpyapp.org/en/guides/video/). So for a landscape phone you crop the
  natural *height* to set the displayed *width*.
- Worked example: 1080x2400 natural, landscape, 3840x2160 (16:9) screen ->
  `--crop=1080:1920:0:240` -> 1920x1080 output -> fills the monitor exactly.
- **Limitation**: rotating the device mid-session does NOT recompute the crop
  (crop is anchored to natural orientation), so the user must restart the
  mirror after rotating. Worth fixing later by recomputing on rotation.

### Verification

`check` + `backendTest` + `guiSmoke` all pass. Orientation regex validated
against the live device's real `dumpsys display` output.

## Follow-up 3: "crop to fill is broken" — adb called without -s

User connected more devices (3 attached: `7e34269d` USB, `192.168.123.128:5555`,
`192.168.123.200:40067`). `cropForScreen()` ran bare `adb shell wm size`, which
fails with `adb: more than one device/emulator`, so the crop came back empty and
silently fell back to Fit — i.e. crop-to-fill appeared to do nothing.

**Rule: every device-targeted adb call must pass `-s <serial>`.** Only global
commands may omit it (`devices -l`, `version`, `connect`, `disconnect <serial>`,
`mdns services`). Fixed both `cropForScreen(String serial)` and
`cropForRatio(String serial, ...)` to use `backend.adb("-s", serial, "shell", ...)`.

### Repo changed under me

Between turns the project was refactored: aspect-ratio logic moved to a new
shared `:core` module (`core/src/main/java/io/github/3togo/scrcaster/core/AspectRatio.java`,
package `io.github.3togo.scrcaster.core`), included via
`desktop/settings.gradle.kts` (`include(":core")`, projectDir `../core`).
`Backend` now delegates `fillCrop/targetRatio/parseRatio/cropForRatio` to it,
and `DesktopApp` gained an `AspectRatio.Ratio` combo (DEVICE, SQUARE, CLASSIC,
WIDE, CUSTOM) + `customRatio` text field with pref keys `ratio`/`ratioCustom`.
Crop precedence in `mirror()`: explicit ratio wins, else Fill.CROP +
fullscreen -> `cropForScreen`, else "". **Re-read files before editing — they
may have changed.**

### Caveat to remember

`--crop` is baked at start from the orientation read at that moment. Device was
portrait (`orientation=0`, 1080x2400) when tested, so crop-to-fill yields
`1080:608:0:896` — a 16:9 band, technically correct but hides most of the
screen. Landscape (as in the user's screenshot) gives the intended
`1080:1920:0:240`. Rotating mid-session does NOT recompute the crop.

### Does the -s bug affect the Android app? No.

Verified: the Android frontend never shells out to a host `adb`.

- `ClientOptions.renderFit` ("FIT"/"STRETCH"/"CROP") and `aspectRatio: Double` are
  **client-side display options** explicitly commented "not sent to the scrcpy
  server".
- `PersistentVideoRenderer.setAspectRatio(target)` just sets `aspectTarget` and
  requests a redraw — the crop is applied at draw time from the real decoded
  frame, so no `wm size` / `dumpsys display` lookup exists to break.
- Device targeting on Android is a **direct ADB socket** to one host:port
  (`DirectAdbClient`, `NativeAdbService`), so there is no "which device?"
  ambiguity to resolve.
- `:core` (`AspectRatio`) holds only pure arithmetic — stateless, no adb, never
  the source of this bug. A *math* bug there would hit both frontends; an adb
  lookup bug is desktop-only by construction.

## Follow-up 4: "crop to fill not working at all" — --crop is broken on the device

Two separate causes:

1. **The fixed build was never installed.** Installed jar (21:46) still had
   `cropForScreen()` with no serial; new build was 22:36. `sudo` has no TTY here,
   so only the user can run `apt install --reinstall`. Two stale DesktopApp
   processes (PIDs 167547/203277) were running from `/usr/share`.

2. **`--crop` does not work on this device at all** (vivo V2343A, Android 15).
   Empirically tested — every variant fails with
   `[server] ERROR: Capture/encoding error: android.media.MediaCodec$CodecException`,
   then scrcpy retries `-m1600` / `-m1280` / `-m1024` and finally streams a
   degraded `1024x576`:
   - `1080:1920:0:240` (correct 16:9 landscape rect) -> fail
   - `1008:1792:36:304` (16-byte aligned) -> fail
   - `1080:2400:0:0` (full-screen no-op crop) -> fail  <-- proves crop itself
   - without `--max-size`, and with `--ignore-video-encoder-constraints` -> fail
   - scrcpy 4.1 (`/usr/local/bin/scrcpy`, first on PATH) AND 3.3.4 (`/usr/bin/scrcpy`)

   So crop-based fill and the AspectRatio presets are unusable on this phone.
   It is a device encoder limitation, NOT a bug in the crop maths.

   **Crop maths independently verified correct**: with the device in landscape,
   feeding the *portrait* rect `1080:608:0:896` produced `Texture: 608x1080` —
   i.e. crop applied in natural orientation then rotated, exactly as the
   scrcpy docs state. The intended landscape rect `1080:1920:0:240` is right.

### Implemented: graceful degradation

`DesktopApp.launch(serial, options, retryWithoutCrop)` now watches scrcpy's
output; on `Capture/encoding error` (only when a crop was actually passed) it
stops the process and relaunches **once** with `crop=""`, so mirroring still
works instead of streaming a broken low-res picture. Logs a clear message.
Guard: `AtomicBoolean.compareAndSet` + `retryWithoutCrop=false` on the retry.

Note `Backend.Options` is a record — use `options.crop()`, not `options.crop`.

### Environment note

Two scrcpy installs: `/usr/local/bin/scrcpy` 4.1 (first on PATH, what the app
uses) and `/usr/bin/scrcpy` 3.3.4. The app resolves bare `scrcpy` via PATH.

**Version guidance: use 4.1.** Verified by running `--help` on each:
- 4.1 has `--render-fit=mode` (letterbox / stretched / unscaled).
- 3.3.4 has **no** `--render-fit` at all.

So the app's "Stretch" fill mode (`--render-fit=stretched`) would fail on 3.3.4
(unknown option). Keep 4.1 first on PATH, or set `SCRCPY=/usr/local/bin/scrcpy`.
`/usr/local/bin` already precedes `/usr/bin`, so the default is correct.
Neither version fixes `--crop` (broken on the V2343A in both).

The deb's `Depends: scrcpy (>= 3.0)` is too lax for the render-fit feature;
left unchanged on purpose — bumping it to >= 4.x would conflict with the
distro's dpkg-tracked 3.3.4 since the 4.1 install is untracked/manual.

## Android app: added "Fullscreen fill" + "Aspect ratio" (client-side, in renderer)

User couldn't find these on Android (only `--fullscreen` toggle + manual `--crop`).
They chose to add BOTH. Implemented client-side in the GL renderer
(`PersistentVideoRenderer`) rather than server-side crop, to avoid needing the
device's natural size / rotation at session start.

- Data model: added to `ScrcpyOptions.Bundle` + DataStore keys + persistence +
  `toClientOptions`, and to `ClientOptions` (client-only, NOT in `ServerParams`):
  - `renderFit` ("FIT"/"STRETCH"/"CROP", default "FIT")
  - `aspectRatio` (Ratio name, default "DEVICE") + `aspectRatioCustom` (String).
  - `ScrcpyOptions.toClientOptions` computes numeric target via new
    `ScrcpyAspectRatio.targetRatioFromName(name, custom)` (device size / orientation
    resolved later by the renderer).
- Renderer `PersistentVideoRenderer`:
  - New `Fit` enum + volatile `fitMode`/`aspectTarget`/`videoW`/`videoH`.
  - `setFitMode/setAspectRatio/setVideoSize/requestRedraw` setters.
  - Shader gained `uTexRect`; `computeTransform(w,h)` = crop source to target ratio
    (oriented to surface), then FIT (letterbox)/STRETCH/CROP into surface.
  - Display surface uses the transform; RECORD surface passes
    `applyDisplayTransform=false` so recordings stay raw.
  - `NativeCoreFacade.init` forwards `addVideoSizeListener` -> `renderer.setVideoSize`.
- Wiring: `Scrcpy.start(options)` calls `NativeCoreFacade.setRenderFit/setAspectRatio`.
- UI: `ScrcpyAllOptionsScreen` — "Fullscreen fill" dropdown after the fullscreen
  switch; "Aspect ratio" dropdown (+ custom text field when CUSTOM) before the crop
  card. Strings added in `values/strings.xml`.
- Build: `./gradlew :app:compileDebugKotlin` BUILD SUCCESSFUL.

### Notes / caveats
- This is a CLIENT-SIDE display crop (no bandwidth saving, unlike server `--crop`).
  If server-side crop is later wanted, compute at `Scrcpy.start` via
  `NativeAdbService.shell("wm size")` + rotation (mirror the desktop flow).
- Aspect-ratio target is oriented to the surface at draw time (landscape vs portrait),
